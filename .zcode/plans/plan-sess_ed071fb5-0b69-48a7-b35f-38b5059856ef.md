## Defense-in-Depth Security Engagement — `claude-skills`

### What this repo is (frames the threat model)
`claude-skills` is a marketplace of 142 Claude Code plugins (almost entirely markdown + a small runtime-code surface). The "users" are developers who install these plugins into their own Claude sessions. **There is no web app, DB, or auth backend.** The real attack surface is: (a) hook scripts that auto-run when a plugin is installed, (b) config-driven subprocess spawning, (c) maintainer scripts that write under `$HOME`, (d) CI/supply chain, (e) the correctness of the defensive-skill *advice* itself, (f) repo governance gaps. We apply a **defense-in-depth / assume-breach / least-privilege / fail-secure** lens throughout.

All work happens in **one worktree** on branch `security/defense-in-depth-audit`. The executing agent will invoke `superpowers:using-git-worktrees` to create it properly, then run everything else inside it.

---

### Phase 0 — Worktree setup
1. Invoke `superpowers:using-git-worktrees`; create worktree `../claude-skills-security-audit` on `security/defense-in-depth-audit` off `main`.
2. Inside the worktree: `mkdir -p docs/security-audit/findings` for per-track findings files.
3. All subsequent phases operate with CWD = the worktree root.

---

### Phase 1 — Parallel security audit (6 read-only subagents, dispatched concurrently)
Each subagent is read-only with respect to repo code and writes **only** its own findings file to `docs/security-audit/findings/<track>.md`. Required output schema per finding: `ID | Severity (Critical/High/Medium/Low/Info) | Title | Location (file:line) | Description | Proof/PoC | Defense-in-depth layer violated | Suggested fix | Effort (S/M/L)`. Severity is calibrated to a *skills marketplace* threat model (auto-running hook RCE = Critical; fail-open guard = High; unpinned installer = Medium; doc typo = Low).

**Track A — Hook & auto-execution scripts.** Scope: `plugins/bun/hooks/**`, `plugins/nuxt-seo/hooks/**` (esp. `detect-nuxt-seo.sh` SessionStart `*` matcher writing to `$CLAUDE_ENV_FILE`), `plugins/claude-code-bash-patterns/scripts/{dangerous-command-guard.py,bash-audit-logger.sh,package-manager-enforcer.sh}`. Focus: fail-open behavior, unsanitized env writes, secret capture in audit logs.

**Track B — Subprocess spawning & config-driven execution.** Scope: `plugins/mcp-dynamic-orchestrator/src/**` (esp. `orchestrator.ts:147` `spawn` from config), any other `child_process`/`execSync`/`spawn` across plugins, `plugins/cloudflare-workers/.../dev-setup.sh:38` (unpinned `curl|bash`). Focus: arbitrary-command-execution paths, command/arg injection, unpinned remote execution.

**Track C — Secret & credential handling.** Scope: `plugins/better-auth/.../generate-secret.sh`, `plugins/cloudflare-zero-trust-access/.../{create-service-token,test-access-jwt}.sh`, `plugins/cloudflare-r2/scripts/**` (credential reads), `process.env` usage across skills, anywhere tokens/keys appear in templates. Focus: secret leakage to stdout/logs, hardcoded creds, insecure defaults, secret handling guidance.

**Track D — Destructive ops & filesystem safety.** Scope: `scripts/install-skill.sh` (`rm -rf` under `$HOME/.claude/skills/`), `scripts/install-all.sh`, `plugins/cloudflare-sandbox/.../setup-sandbox-binding.sh` (edits user `wrangler.jsonc`), all `rm -rf`/`chmod`/symlink writes. Focus: path traversal, destructive ops outside repo without guardrails, missing confirmation/rollback.

**Track E — CI/CD & supply chain.** Scope: `.github/workflows/**`, `package.json`, `package-lock.json`, `.githooks/**`, `scripts/review-skill.sh` (SSRF-ish curl), `scripts/fix-frontmatter.mjs` (hardcoded `/Users/eddie/...`). Focus: missing scanners (CodeQL/secret-scan/dependency-review/npm-audit), expression injection, unpinned action versions, the `fast-json-patch` override integrity, postinstall hooks.

**Track F — Defensive skill content correctness + injection surfaces.** Scope: `plugins/{xss-prevention,csrf-protection,api-security-hardening,defense-in-depth-validation,vulnerability-scanning,access-control-rbac,cybersecurity}/**` — verify the *advice* and shipped *code examples* are themselves safe (no vulnerable "example" code, no unsafe OSS-tool invocation defaults, authorization-gate integrity in `cybersecurity`). Also covers injection: shell injection in `detect-nuxt-seo.sh`, SSRF in `review-skill.sh`. Focus: the security skills must not teach/ship insecure patterns.

### Phase 2 — Triage & fix-task enumeration (controller, no subagent)
1. Read all 6 findings files; deduplicate; rank into a single consolidated report `docs/security-audit/REPORT.md` with a severity matrix.
2. Decompose every Critical/High/Medium/Low finding into discrete SDD tasks (one concern per task). Info-only items get noted in the report but no code change unless trivial. Each task gets a short spec: location, the exact fix, acceptance criteria.
3. Create a `TodoWrite` list of all fix tasks, sequenced so that infra/governance tasks (CI scanners, SECURITY.md) land first, then per-file fixes, so later fixes benefit from the new guardrails.

Realistic task count: ~15–25 (6 known issues from Phase-0 exploration + audit-discovered ones). Examples already identified: fail-closed guard, sanitize env-file writes, `$HOME` path guardrails in install scripts, derive `REPO_ROOT` from cwd, restrict `review-skill.sh` curl, validate MCP-spawn config, pin/checksum the bun installer, redact secrets in audit log, add CI CodeQL+secret-scan+dep-review+npm-audit, add `SECURITY.md`, add plugin security-review checklist, fix any unsafe defensive-skill examples.

---

### Phase 3 — Fix phase (Subagent-Driven Development, sequential)
For **each** fix task, in order:
1. Dispatch **implementer** subagent (per `implementer-prompt.md`) with full task text + the worktree path as CWD. It implements, self-reviews, and commits on the `security/defense-in-depth-audit` branch. Model chosen by complexity (cheap for 1–2 file mechanical fixes; capable for CI/multi-file).
2. Dispatch **spec-compliance reviewer** (`spec-reviewer-prompt.md`); loop fixes until ✅ matches the finding's acceptance criteria — no over/under-build.
3. Dispatch **code-quality reviewer** (`code-quality-reviewer-prompt.md`); loop until approved.
4. Mark task complete in `TodoWrite`; proceed to next.

SDD red flags honored: **never** dispatch multiple implementer subagents in parallel (write conflicts on one shared branch); spec review before quality review; never skip re-review; never start fixes on `main` (we're on the worktree branch).

Governance/CI tasks are first in the sequence so they're in place before content fixes are reviewed.

---

### Phase 4 — Final review & branch completion
1. Dispatch a **final code-review subagent** over the entire diff on `security/defense-in-depth-audit` (using `superpowers:requesting-code-review` framing) — checks cross-cutting consistency, that no fix reintroduced a risk, and that the audit report matches what was actually fixed.
2. Invoke `superpowers:finishing-a-development-branch`: summarize the engagement, leave the branch ready (commit log clean, `REPORT.md` finalized), and surface the PR description for the user. **No push/merge without explicit user OK.**

---

### Deliverables (all in the worktree, on the branch)
- `docs/security-audit/findings/<track>.md` × 6 — raw per-track findings
- `docs/security-audit/REPORT.md` — consolidated, ranked, with status per finding (Fixed / Accepted-risk / Info)
- Code/config fixes across hooks, scripts, plugins, CI
- New `SECURITY.md`, plugin security-review checklist, hardened CI workflows
- A clean branch `security/defense-in-depth-audit` ready for review/PR

### Notes / guardrails
- The cybersecurity skill's *authorization gate* governs offensive live-target testing — **not applicable here**; this is a defensive static audit (its "Track A — always allowed"). No live-target offensive work will be performed.
- No commits/push to `main`. All work stays on the worktree branch until you approve.
- "Fix everything" is bounded by what the audit actually finds; if a finding is genuinely a non-issue after deeper analysis, the report records it as Accepted-risk with reasoning rather than forcing a change.
